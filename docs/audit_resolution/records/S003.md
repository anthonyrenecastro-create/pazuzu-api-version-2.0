# S003 — 'Threshold, not wall' lacks ROC operating points

- **Audit ID:** S003 (source issue #3)
- **Title:** 'Threshold, not wall' lacks ROC operating points
- **Classification:** [MTH]
- **Severity:** medium
- **Severity rationale:** Without false-accept/reject operating points the claim is marketing language, not an engineering spec.

## Original defect description
The 'threshold, not wall' doctrine claims graded rejection, but provides no ROC curve analysis and no specified False Reject / False Accept operating points, making it an untestable metaphor.

## Affected subsystem
Doctrine / S3 Dual Ward

## Root cause
The v1.0 formalism asserted a property without defining its measurement procedure.

## Proposed correction
Require every scoring station to publish an ROC evaluated on a labeled benchmark, and pin operating points in config/thresholds.yaml (FRR/FAR targets per station); docs/doctrine.md defines 'threshold' as these numbers or nothing.

## Implementation files
- `config/thresholds.yaml`
- `pipeline/eval/roc.py`
- `docs/doctrine.md`

## Verification method
pytest tests/unit/test_eval.py::test_thresholds_have_roc_operating_points

## Test identifier
tests/unit/test_eval.py::test_thresholds_have_roc_operating_points

## Status
implemented_unverified

## Status justification
Eval harness and config schema are specified in v2.0 but the labeled benchmark does not exist yet; nothing is verified. The supplied source references 'eight fatal defects' but does not enumerate which of the 144 issues are fatal; therefore no fatal status is assigned anywhere in this registry.

## Residual risk
Operating points chosen without production data may misprice the reject/accept trade-off on day one.
