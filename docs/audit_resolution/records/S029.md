# S029 — No page-fault handling for KV-cache tier migration races

- **Audit ID:** S029 (source issue #29)
- **Title:** No page-fault handling for KV-cache tier migration races
- **Classification:** [PERF]
- **Severity:** high
- **Severity rationale:** A hot-memory request racing a warm→hot migration can read stale or missing pages.

## Original defect description
KV-cache tiering (hot/warm/cold) requires a complex async memory mover, but there is no spec for handling a page fault when hot memory is requested while it is still migrating from warm.

## Affected subsystem
S2 Sexagesimal Turn

## Root cause
v1.0 specified the tiers without the concurrency protocol between them.

## Proposed correction
Implement a page-state machine (resident/migrating/faulted) with synchronous fault handling in stations/s02_turn/kvcache.py: a request for a migrating page blocks on the migration fence or triggers priority promotion, never reads a torn page.

## Implementation files
- `stations/s02_turn/kvcache.py`

## Verification method
pytest tests/unit/test_s02.py::test_page_fault_during_migration

## Test identifier
tests/unit/test_s02.py::test_page_fault_during_migration

## Status
scheduled

## Status justification
The memory mover itself is not yet designed in detail; scheduled with the tiering implementation. The supplied source references 'eight fatal defects' but does not enumerate which of the 144 issues are fatal; therefore no fatal status is assigned anywhere in this registry.

## Residual risk
Fault handling adds latency on the hot path; the fence must be measured, not assumed.
